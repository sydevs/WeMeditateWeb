# Implement Issue

End-to-end implementation of a GitHub issue for **WeMeditateWeb** (Vike + React + TypeScript + Cloudflare Workers frontend that consumes the SahajCloud PayloadCMS over REST):

read → plan → branch → implement → test → validate → **finalize** (simplify → code-review → push → PR → CI). The finalize pipeline is the shared `/finalize-pr` skill — this is **phase 1** of the 3-phase PR workflow (see `CLAUDE.md` → "PR Workflow (3 Phases)").

## Stack quick reference

- **Package manager:** pnpm (never npm/yarn).
- **Build:** `pnpm build` (vike build). **Deploy:** `pnpm deploy`. **Local Workers runtime:** `pnpm prod`.
- **Lint:** `pnpm lint` (`eslint .`). **Types:** `pnpm typecheck` (`tsc --noEmit`). **Tests:** `pnpm test:run` (Vitest, single run).
- **CMS types:** `server/payload-types.ts` is generated by `pnpm types:cms` — never hand-edit it.
- **No** database, migrations, collections, Playwright, or jsdom here — this app *consumes* the CMS. See CLAUDE.md "Testing".
- **CI:** GitHub Actions runs on every PR (`.github/workflows/ci.yml`) — a `gate` job (`pnpm lint` / `pnpm typecheck` / `pnpm test:run`, unit only) plus a `smoke` matrix that fetch-tests the deployed Cloudflare previews; two Cloudflare previews (web Worker + Ladle Pages) also build per PR. The **finalize** step (`/finalize-pr`) pushes and watches all of these — the local validation gate (step 8) keeps the implement loop fast. See [.claude/docs/cloudflare-previews-ci.md](../../docs/cloudflare-previews-ci.md).

## Invocation


## Workflow

### 1. Verify clean working tree

```bash
git status
```

If there are uncommitted changes that aren't yours, **stop**. Ask the user whether to stash or proceed. Never silently overwrite their work.

### 2. Fetch the issue

```bash
gh issue view "$ISSUE" --json number,title,body,labels,assignees
```

Read it fully. Identify:

- Acceptance criteria (checklist at the bottom)
- Files-affected list (if present)
- Whether new/changed CMS fields are required (affects `pnpm types:cms`)
- Whether tests are explicitly required

If the issue lacks acceptance criteria, **ask the user** what "done" looks like before starting. Don't guess.

### 3. Plan the work

Lay out the plan in the conversation before touching code:

- Files to create / modify
- Order of changes
- Whether tests need to be written (almost always yes)
- Whether CMS types need regenerating (`pnpm types:cms`)
- Estimated number of commits

Ask the user to confirm the plan. Iterate until aligned.

### 4. Create a branch

See `branch-naming.md` for naming. Format `<type>/<short-slug>`. Branch from latest `main`:

```bash
git fetch origin main && git checkout main && git pull && git checkout -b <branch>
# e.g., git checkout -b feat/lectures-hls-renderer
# e.g., git checkout -b fix/meditation-frame-selection
```

### 5. Implement

One unit of change at a time. After each meaningful unit:

```bash
git add <files>
git commit -m "<conventional commit message>"
```

**Commit message rules** (see `.claude/skills/draft-ticket/conventions.md`):

- `<type>(<scope>): <subject>` — same format as the issue title
- Imperative mood, ≤ 70 chars, lowercase subject
- Reference the issue in the body, not the subject: `Refs #24` or `Closes #24`
- End with the Co-Authored-By trailer from the project's commit guidance

**HEREDOC for multi-line bodies** — always:

```bash
git commit -m "$(cat <<'EOF'
feat(cms): fetch related content for meditations

Closes #26

Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
EOF
)"
```

### 6. CMS types (if the work depends on new CMS fields)

This app does not own the CMS schema — it consumes it. If your change relies on CMS fields that aren't yet in the local types:

```bash
pnpm types:cms   # curls the latest payload-types.ts from SahajCloud and strips augmentation
```

- **Never** hand-edit `server/payload-types.ts` (a hook blocks this). To change the shape, the upstream SahajCloud schema must change.
- There are **no migrations** in this repo. App-specific types belong in `server/cms-types.ts`.

### 7. Write tests

This project runs **Vitest only**, `environment: 'node'`, with tests co-located next to source (`Foo.tsx` → `Foo.test.tsx`). There is **no jsdom, no Testing Library, no Playwright** — do not add them. See CLAUDE.md "Testing" and `test-plan-checklist.md`.

For each acceptance-criterion item that can be tested:

- **Pure utilities / logic** (parsing, transforms, URL builders) — unit tests. Highest value. See [lib/cloudflare-images.test.ts](../../../lib/cloudflare-images.test.ts).
- **Component contracts** — assert on rendered markup via `renderToStaticMarkup` from `react-dom/server` (attributes, conditional children, accessibility markers). See [components/atoms/Image/Image.test.tsx](../../../components/atoms/Image/Image.test.tsx). Note: `useState`/`useMemo` work under SSR but `useEffect` does not — assert against first-render state.
- **CMS data fetching** (`server/cms-client.ts`) — cover error/empty paths and that caching keys/TTLs are respected.
- **Interactive behavior** (hover/focus/click) — cannot be simulated without a DOM; verify visually in Ladle (`pnpm ladle`) instead.

### 8. Validate (lean local gate)

Run the lean gate as you implement — it keeps the loop fast and catches failures before they reach finalize. The full CI gate + Cloudflare preview builds run in the finalize step (step 9). Run it via the validation script:

```bash
.claude/skills/implement-issue/scripts/validate.sh          # lint + tsc --noEmit + pnpm test:run
.claude/skills/implement-issue/scripts/validate.sh --full   # the above + pnpm build (mirrors the Cloudflare preview build)
```

Or manually:

```bash
pnpm lint
pnpm exec tsc --noEmit
pnpm test:run
```

Use `--full` before finalizing anything that touches build config, server entry, Vike config, or Cloudflare/Wrangler setup — `pnpm build` is the closest local mirror of what the preview deployment runs.

If anything fails: fix it, commit the fix as a separate commit, and re-run validation.

### 9. Finalize — run the ship pipeline

Implementation is done and locally validated. Now ship it via the **finalize pipeline**: **follow every step in [.claude/skills/finalize-pr/SKILL.md](../finalize-pr/SKILL.md)** — simplify → a single `/code-review` → conditional `/security-review` → lean gate → push → open the PR → watch CI (with capped fixes) → report. On this first run it **creates** the PR.

Execute that skill's steps directly here; don't re-implement them in this file — `finalize-pr` is the single source of truth, so the exact same pipeline runs whether the user types `/finalize-pr` or `/implement-issue`.

### 10. Hand off to the Adjust phase

Once the PR is open and CI is green, report the PR URL, CI status, and any manual-verification items (UI in Ladle, browser behaviour via Puppeteer, content/locale edge cases). Then note that we're now in the **Adjust phase**: further changes are committed locally as we go but **not pushed**; the user runs `/finalize-pr` again when the PR is ready to re-review and re-run CI. See "PR Workflow (3 Phases)" in `CLAUDE.md`.

## Hard rules

- **Never** force-push to main or any shared branch
- **Never** skip hooks (`--no-verify`)
- **Never** hand-edit `server/payload-types.ts` — regenerate with `pnpm types:cms`
- **Never** use npm/yarn — this is a pnpm project
- **Never** commit secrets / `.env` / credentials
- **Never** add jsdom, Testing Library, or Playwright without discussing first
- **Always** create commits incrementally; never one monolithic commit at the end
- **Always** run the lean local gate (step 8) as you implement
- **Always** ship via the finalize pipeline ([.claude/skills/finalize-pr/SKILL.md](../finalize-pr/SKILL.md)) — never hand-roll the push/PR/CI steps here, and never report the PR ready while CI is red

## Edge cases

### Issue is too vague

If acceptance criteria are missing or ambiguous, stop at step 3 and ask the user. Don't invent your own ACs and proceed.

### Existing PR for this issue

Run `gh pr list --search "<keyword>"` before step 4. If a PR already exists, ask whether to extend it (check it out) or open a new one.

### Pre-existing failures on `main`

If lint/types/tests already fail on `main` (not caused by your change), follow the fast-verification recipe in `.claude/skills/pr-prep/SKILL.md`, fix it in your PR, and note it in the report.

### Change needs CMS fields that don't exist yet upstream

The CMS schema lives in the SahajCloud repo, not here. If your change depends on fields that aren't in the CMS yet, stop and surface it — implement only the part that the current schema supports, and file a follow-up for the upstream schema change.

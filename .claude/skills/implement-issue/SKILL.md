# Implement Issue

End-to-end implementation of a GitHub issue for **WeMeditateWeb** (Vike + React + TypeScript + Cloudflare Workers frontend that consumes the SahajCloud PayloadCMS over REST):

read → plan → **worktree** → implement → test → validate → **finalize** (simplify → code-review → docs sync → push → PR → CI) → **clean up**. Work happens in an isolated git worktree by default (the main checkout stays free; several issues can run in parallel). The finalize pipeline is the shared `/finalize-pr` skill — this is **phase 1** of the 3-phase PR workflow (see `CLAUDE.md` → "PR Workflow (3 Phases)"). Once the PR is open and green, the worktree is removed and you sign off with a copy/paste command that switches the branch into the main checkout for local review.

## Stack quick reference

- **Package manager:** pnpm (never npm/yarn).
- **Build:** `pnpm build` (vike build). **Deploy:** `pnpm deploy`. **Local Workers runtime:** `pnpm prod`.
- **Lint:** `pnpm lint` (`eslint .`). **Types:** `pnpm typecheck` (`tsc --noEmit`). **Tests:** `pnpm test:run` (Vitest, single run).
- **CMS types:** `server/payload-types.ts` is generated by `pnpm types:cms` — never hand-edit it.
- **No** database, migrations, collections, Playwright, or jsdom here — this app *consumes* the CMS. See CLAUDE.md "Testing".
- **CI:** GitHub Actions runs on every PR (`.github/workflows/ci.yml`) — a `gate` job (`pnpm lint` / `pnpm typecheck` / `pnpm test:run`, unit only) plus a `smoke` matrix that fetch-tests the deployed Cloudflare previews; two Cloudflare previews (web Worker + Ladle Pages) also build per PR. The **finalize** step (`/finalize-pr`) pushes and watches CI — the local validation gate (step 8) keeps the implement loop fast. See [.claude/docs/cloudflare-previews-ci.md](../../docs/cloudflare-previews-ci.md).


## Workflow

### 1. Verify clean working tree

```bash
git status
```

If there are uncommitted changes that aren't yours, **stop**. Ask the user whether to stash or proceed. Never silently overwrite their work.

### 2. Fetch the issue

```bash
gh issue view "$ISSUE" --json number,title,body,labels,assignees
```

Read it fully. Identify:

- Acceptance criteria (checklist at the bottom)
- Files-affected list (if present)
- Whether new/changed CMS fields are required (affects `pnpm types:cms`)
- Whether tests are explicitly required

If the issue lacks acceptance criteria, **ask the user** what "done" looks like before starting. Don't guess.

### 3. Plan the work

Lay out the plan in the conversation before touching code:

- Files to create / modify
- Order of changes
- Whether tests need to be written (almost always yes)
- Whether CMS types need regenerating (`pnpm types:cms`)
- Estimated number of commits

Post the plan, then **proceed immediately** when the issue has clear acceptance criteria and the plan follows them — don't wait for a confirmation that adds nothing.

**Pause and ask** only when:

- acceptance criteria are missing or the issue is silent on what "done" means;
- scope is ambiguous (more than one reasonable reading of the ticket);
- the plan **deviates** from the ticket (extra scope, a different approach than the issue prescribes, a dropped criterion);
- the work is **destructive** (deletes/renames existing surfaces, changes public behaviour beyond the ticket, touches secrets or deploy config).

### 4. Create a worktree (default) + branch

Work in an **isolated git worktree** by default. Use the **EnterWorktree** tool — it branches fresh from `origin/main` under `.claude/worktrees/` and switches the session into the worktree. Only run in the current checkout instead if the user passes `--no-worktree` or explicitly says "no worktree" (then branch the old way: `git fetch origin main && git checkout main && git pull && git checkout -b <type>/<slug>`).

1. `EnterWorktree` with `name` set to the branch slug (see `branch-naming.md`), e.g. `feat/lectures-hls-renderer`.
2. It auto-names the branch `worktree-<slug-with-/-as-+>`; rename it to the convention (`git branch --show-current` shows the auto name):

   ```bash
   git branch -m <auto-generated-name> <type>/<slug>
   ```

**Worktree setup — the session cwd is now the worktree; edit files there, not the main checkout** (a stray edit to the main checkout pollutes the wrong branch and won't be served by the worktree's dev server):

- A worktree has **no `node_modules`** — run `pnpm install` in it before the lean gate, `pnpm dev`, or `pnpm ladle` (fast; pnpm hardlinks from its store).
- `.env` / `.env.local` and `.dev.vars` are **gitignored**, so they're absent in the worktree. Copy them from the main checkout root **only if a local run is needed** (`pnpm dev`, `pnpm prod`, or anything that hits the CMS): `cp <main-checkout>/.env.local ./.env.local` (stays gitignored). The lean gate itself doesn't need them.

### 5. Implement

One unit of change at a time. After each meaningful unit:

```bash
git add <files>
git commit -m "<conventional commit message>"
```

**Commit message rules** (see `.claude/skills/draft-ticket/conventions.md`):

- `<type>(<scope>): <subject>` — same format as the issue title
- Imperative mood, ≤ 70 chars, lowercase subject
- Reference the issue in the body, not the subject: `Refs #24` or `Closes #24`
- End with the Co-Authored-By trailer from the project's commit guidance

**HEREDOC for multi-line bodies** — always:

```bash
git commit -m "$(cat <<'EOF'
feat(cms): fetch related content for meditations

Closes #26

Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
EOF
)"
```

### 6. CMS types (if the work depends on new CMS fields)

This app does not own the CMS schema — it consumes it. If your change relies on CMS fields that aren't yet in the local types:

```bash
pnpm types:cms   # curls the latest payload-types.ts from SahajCloud and strips augmentation
```

- **Never** hand-edit `server/payload-types.ts` (a hook blocks this). To change the shape, the upstream SahajCloud schema must change.
- There are **no migrations** in this repo. App-specific types belong in `server/cms-types.ts`.

### 7. Write tests

This project runs **Vitest only**, `environment: 'node'`, with tests co-located next to source (`Foo.tsx` → `Foo.test.tsx`). There is **no jsdom, no Testing Library, no Playwright** — do not add them. See CLAUDE.md "Testing" and `test-plan-checklist.md`.

For each acceptance-criterion item that can be tested:

- **Pure utilities / logic** (parsing, transforms, URL builders) — unit tests. Highest value. See [lib/cloudflare-images.test.ts](../../../lib/cloudflare-images.test.ts).
- **Component contracts** — assert on rendered markup via `renderToStaticMarkup` from `react-dom/server` (attributes, conditional children, accessibility markers). See [components/atoms/Image/Image.test.tsx](../../../components/atoms/Image/Image.test.tsx). Note: `useState`/`useMemo` work under SSR but `useEffect` does not — assert against first-render state.
- **CMS data fetching** (`server/cms-client.ts`) — cover error/empty paths and that caching keys/TTLs are respected.
- **Interactive behavior** (hover/focus/click) — cannot be simulated without a DOM; verify visually in Ladle (`pnpm ladle`) instead.

### 8. Validate (lean local gate)

Run the lean gate as you implement — it keeps the loop fast and catches failures before they reach finalize. The full CI gate + Cloudflare preview builds run in the finalize step (step 9). Run it via the validation script:

```bash
.claude/skills/pr-prep/check.sh          # lint + tsc --noEmit + pnpm test:run
.claude/skills/pr-prep/check.sh --full   # the above + pnpm build (mirrors the Cloudflare preview build)
```

Or manually:

```bash
pnpm lint
pnpm exec tsc --noEmit
pnpm test:run
```

Use `--full` before finalizing anything that touches build config, server entry, Vike config, or Cloudflare/Wrangler setup — `pnpm build` is the closest local mirror of what the preview deployment runs.

If anything fails: fix it, commit the fix as a separate commit, and re-run validation.

### 9. Finalize — run the ship pipeline

Implementation is done and locally validated. Now ship it via the **finalize pipeline**: **follow every step in [.claude/skills/finalize-pr/SKILL.md](../finalize-pr/SKILL.md)** — simplify → a single `/code-review` → conditional `/security-review` → lean gate → docs sync → push → open the PR → watch CI (with capped fixes) → report. On this first run it **creates** the PR.

Execute that skill's steps directly here; don't re-implement them in this file — `finalize-pr` is the single source of truth, so the exact same pipeline runs whether the user types `/finalize-pr` or `/implement-issue`.

### 10. Remove the worktree

Once the finalize pipeline has **opened the PR and CI is green**, tear the worktree down — the branch's commits are safe on `origin`, so nothing is lost:

1. Confirm the branch is fully pushed; **abort the removal** if it isn't:

   ```bash
   [ "$(git rev-parse HEAD)" = "$(git rev-parse origin/<branch>)" ] && echo pushed
   ```

2. Remove it with the **ExitWorktree** tool (`action: "remove"`, `discard_changes: true` — the commits live on `origin`, not the original branch, so the tool needs this to proceed). This deletes the worktree dir + its local branch and returns the session to the main checkout.

Skip this only if the user opted out of the worktree at step 4.

### 11. Final summary — required template

End your final message with the block below (fill every `<placeholder>`), so runs sign off consistently. The **Adjust phase now happens in the main checkout**: the user runs the switch command to pick the branch up locally, commits further changes without pushing, and re-runs `/finalize-pr` (which re-pushes + re-runs CI). See "PR Workflow (3 Phases)" in `CLAUDE.md`.

```markdown
---
✅ **Ready for review — <type>(<scope>): <subject>**

[PR #<n>](<pr-url>) · CI green · built in an isolated worktree (now removed).

**Continue locally** (Adjust phase — commit changes, then `/finalize-pr` to re-run CI):

    git fetch origin <branch> && git switch <branch>

**Verify manually:** <one line — UI in Ladle, browser behaviour via Puppeteer, or content/locale edge cases the unit lane can't cover; or "none">
---
```

## Hard rules

- **Never** force-push to main or any shared branch
- **Never** skip hooks (`--no-verify`)
- **Never** hand-edit `server/payload-types.ts` — regenerate with `pnpm types:cms`
- **Never** use npm/yarn — this is a pnpm project
- **Never** commit secrets / `.env` / credentials
- **Never** add jsdom, Testing Library, or Playwright without discussing first
- **Always** create commits incrementally; never one monolithic commit at the end
- **Always** run the lean local gate (step 8) as you implement
- **Always** ship via the finalize pipeline ([.claude/skills/finalize-pr/SKILL.md](../finalize-pr/SKILL.md)) — never hand-roll the push/PR/CI steps here, and never report the PR ready while CI is red
- **Always** work in a worktree by default (EnterWorktree); only skip on `--no-worktree` or an explicit user opt-out
- **Always** edit files in the worktree, never the main checkout
- **Always** remove the worktree once the PR is open and CI is green (ExitWorktree), after confirming the branch is fully pushed
- **Always** close with the step 11 final-summary template

## Edge cases

### Issue is too vague

Step 3 auto-proceeds on a clear ticket. If acceptance criteria are **missing or ambiguous** — or the plan you'd write deviates from the ticket, or the work is destructive — stop at step 3 and ask the user. Don't invent your own ACs and proceed.

### Existing PR for this issue

Run `gh pr list --search "<keyword>"` before step 4. If a PR already exists, ask whether to extend it (check it out) or open a new one.

### Pre-existing failures on `main`

If lint/types/tests already fail on `main` (not caused by your change), follow the fast-verification recipe in `.claude/skills/pr-prep/SKILL.md`, fix it in your PR, and note it in the report.

### Change needs CMS fields that don't exist yet upstream

The CMS schema lives in the SahajCloud repo, not here. If your change depends on fields that aren't in the CMS yet, stop and surface it — implement only the part that the current schema supports, and file a follow-up for the upstream schema change.
